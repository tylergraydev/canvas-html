What is HTML in Canvas?

For 20 years a <canvas> has been a one-way pixel buffer: you draw into it, and whatever you drew is just colored dots — no text, no buttons, no accessibility. Chrome's HTML-in-Canvas origin trial changes that. It lets you paint a live, interactive, accessible DOM subtree straight into the canvas bitmap. The card on the right is real HTML — painted by the canvas, yet you can still type in it, click it, and tab to it.

The problem

Canvas and the DOM each give you half of what you want.

  • Canvas is fast and pixel-perfect — great for games, charts, shaders, 3D. But everything you draw is dead pixels: not selectable, not focusable, invisible to screen readers, no real inputs.
  • The DOM is rich and accessible — text reflows, inputs work, a screen reader can read it. But it's hard to bend in 3D, warp, reflect, or feed into a shader.

Historically, to put a UI "in" a canvas you rebuilt it by hand with fillText/fillRect, or rasterized it to a frozen image. Either way you threw away the interactivity and the accessibility.

The idea

Put your real HTML inside the canvas and let the browser keep laying it out and handling its events. Then, each time the canvas needs to repaint, ask it to stamp that element's current pixels into the bitmap. The element stays live; the canvas just gets a picture of it that's always up to date.

Because the element is still a real DOM node, focus rings, the tab order, text selection and the accessibility tree all keep working — the canvas is now just the visual surface. The whole demo below — markup and script — is shown verbatim on the right.

The mental model — three moving parts

          

            

              01
              
<canvas layoutsubtree>

              
The layoutsubtree attribute tells the browser to lay out the canvas's
                DOM children as if they were a normal part of the page.

            

            

              02
              
canvas.onpaint

              
Fires whenever the canvas needs to repaint — a DOM mutation inside it, a keystroke,
                a focus change. This is your render loop; usually no requestAnimationFrame.

            

            

              03
              
the returned transform

              
drawElementImage() hands back a matrix mapping the element's box to where
                you painted it. Assign it to element.style.transform so clicks and focus
                rings land on the painted pixels.

            

          

        


        

          
Two entry points — it is not 2D-only

          
The trial adds an element overload to both canvas context types.

          

            

              
2D — drawElementImage

              
Paints the element into the 2D bitmap and returns its transform. Used by most demos.


const ctx = canvas.getContext('2d');

canvas.onpaint = () => {
  ctx.reset();
  // draw your own backdrop, then the element
  const t = ctx.drawElementImage(card, x, y);
  card.style.transform = t.toString();
};

            

            

              
WebGL — texElementImage2D

              
Uploads the live element straight to the GPU as a texture for use on real 3D geometry.


const gl = canvas.getContext('webgl2');
gl.bindTexture(gl.TEXTURE_2D, tex);

// mirrors texImage2D's element overload
gl.texElementImage2D(
  gl.TEXTURE_2D, 0, gl.RGBA,
  gl.RGBA, gl.UNSIGNED_BYTE, card);
